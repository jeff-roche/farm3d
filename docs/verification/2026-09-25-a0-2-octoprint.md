## Live instance

The repo owner approved OctoPrint in a container, running its bundled
Virtual Printer, as the live instance for this issue. **The printer is a
virtual printer, not physical hardware.** It exercises OctoPrint's real
REST server, access control, serial state machine, job reporting, and
409 behavior. It does not exercise a real serial link, real firmware, or a
real heater.

| Item | Value |
| --- | --- |

| Container runtime | podman 6.1.2 (rootless) |

### Reproducing the instance

Rootless podman in this environment has no `/dev/net/tun`, so port
publishing (`-p`) fails. With host networking, the image's haproxy cannot
bind port 80, but OctoPrint itself still serves on 5000:

```sh
podman run -d --name farm3d-a02-octoprint --network host docker.io/octoprint/octoprint:latest

B=/octoprint/octoprint
podman exec farm3d-a02-octoprint octoprint --basedir $B user add --password <password> --admin farm3d
podman exec farm3d-a02-octoprint octoprint --basedir $B config set --bool plugins.virtual_printer.enabled true
podman exec farm3d-a02-octoprint octoprint --basedir $B config set --bool server.firstRun false          # skip the setup wizard
podman exec farm3d-a02-octoprint octoprint --basedir $B config set --bool server.onlineCheck.enabled false
podman restart farm3d-a02-octoprint
```

To create an Application Key, log in with a CSRF token, then call the
appkeys plugin:

```sh
curl -s -c cj -b cj -o /dev/null http://127.0.0.1:5000/                 # sets the csrf_token_P5000 cookie
TOKEN=$(awk '/csrf_token/ {print $7}' cj)
curl -s -c cj -b cj -H "X-CSRF-Token: $TOKEN" -H 'Content-Type: application/json' \
  -d '{"user":"farm3d","pass":"<password>","remember":false}' http://127.0.0.1:5000/api/login
curl -s -c cj -b cj -H "X-CSRF-Token: $TOKEN" -H 'Content-Type: application/json' \
  -d '{"command":"generate","app":"farm3d-a02-validation"}' http://127.0.0.1:5000/api/plugin/appkeys > appkey.json
# appkey.json → {"api_key": "...", "app_id": ..., "user_id": ...}. Keep it out of the repo.
```

To connect the virtual printer (`autoconnect` makes it reconnect after a
container restart):

```sh
curl -s -H "X-Api-Key: $KEY" -H 'Content-Type: application/json' \
  -d '{"command":"connect","port":"VIRTUAL","baudrate":115200,"printerProfile":"_default","autoconnect":true}' \
  http://127.0.0.1:5000/api/connection
```

To stop and remove the instance:

```sh
podman stop farm3d-a02-octoprint && podman rm farm3d-a02-octoprint
```

## Live evidence

Command (the key comes from the environment and is never printed):

```sh
FARM3D_OCTOPRINT_HOST=127.0.0.1 FARM3D_OCTOPRINT_PORT=5000 FARM3D_OCTOPRINT_API_KEY=<key> \
  just test-octoprint-live
```

It runs three ignored tests from `src-tauri/tests/a0_octoprint_live.rs`.

### 1. Printer disconnected from OctoPrint (`Closed`): the 409 path

`GET /api/printer` returned **HTTP 409** (checked directly with curl).
`GET /api/job` returned `"state": "Offline"` and every job and progress
field was `null`. That matches the documented shape the fixtures use.

```text
probe: {"kind":"octoprint","hostSoftware":"1.11.8","firmware":"","reportedName":"Default","state":"Closed",
        "stateMessage":"","reported":{"bedWidthMm":200.0,"bedDepthMm":200.0,"printableHeightMm":200.0}}
telemetry: {"hostActivity":"unknown","hostActivityName":"Offline"}
health: Offline at 2026-09-25T17:46:27Z      (then every 2 s)
wrong key: Auth("HTTP 403")
```

The poll loop kept running with no temperatures. It did not report an error.

### 2. Printing (virtual print of a 245-line dwell/move G-code file)

OctoPrint reported `completion: 24.90272373540856` (a 0–100 percentage)
a few seconds before farm3d read:

```text
telemetry: {"hostActivity":"printing","hostActivityName":"Printing","jobName":"a02-validation.gcode",
            "progress":0.25713359273670555,"nozzleTempC":147.32,"nozzleTargetC":215.0,
            "bedTempC":60.0,"bedTargetC":60.0,"printDurationS":14.0}
```

This is the plan's highest-risk check. The live completion is a
percentage, and farm3d reports it as a 0..=1 fraction.

### 3. Setup, credential, supervision, and restart through the Tauri IPC path

`live_octoprint_setup_supervision_and_restart_through_ipc` calls the real
`probe_connection` and `create_printer` commands. It uses the production
connection factory and a file-backed credential store in a temp profile.
It then stops the supervisor and restores it through
`restore_persisted_connections` over the same database and credential
store, the same path `lib.rs` uses at startup.

```text
created: setupGaps=[] connection={"credentialRef":"farm3d/credential/3169…","host":"127.0.0.1","kind":"octoprint","port":5000,"useTls":false}
status:  {"connectionState":"online","telemetry":{"hostActivity":"idle","hostActivityName":"Operational",...},
          "operationalState":"ready","readiness":{"state":"ready"},"freshness":"fresh",...}
after restart (before first poll): {"connectionState":"connecting",...,"freshness":"stale"}   (hydrated from cache)
resumed: {"connectionState":"online",...,"operationalState":"ready","freshness":"fresh"}
key scan: 13 surfaces checked (IPC responses, 4 status events, database, WAL, metadata/data dirs); key absent from all
```

With the printer disconnected, the same test reported `connectionState:
"offline"` and `operationalState: "offline"` both before and after the
restart, and set no `error`.

Observation: after a job finishes, OctoPrint keeps reporting the last file
at `completion: 100` while `state` is `Operational`. farm3d passes that
through as it is: the Printer is Ready and the last job shows 100%. That
matches OctoPrint's own UI.

## Remaining human checks

These need someone at the display. An agent-driven attempt was abandoned:
there is no input automation, and screenshotting the desktop captures
unrelated windows.

1. **Status display in the real app.** Run `just dev`, add a Printer, and
   pick **OctoPrint** in Connection. Enter host `127.0.0.1`, port `5000`,
   and the Application Key. **Test connection** should show
   `Operational` and `Default — 1.11.8`. Save. The Monitor card should go
   Connecting → Ready, and temperatures should update every ~2 s. Start a
   print from OctoPrint's UI (`http://127.0.0.1:5000`). The card should
   show Printing, and its progress should equal OctoPrint's percentage
   ÷ 100. Disconnect the printer in OctoPrint's Connection panel. The card
   should show Offline with temperatures as "—", not an error. Quit and
   relaunch farm3d. The Printer should reconnect without you opening its
   Connection tab. Use a throwaway profile, or remove the Printer
   afterwards. This writes the key to your real keychain.
2. **Discovery.** Check whether **Discovered on this network** lists the
   instance (`_octoprint._tcp`). A host-networked container may or may
   not advertise mDNS. If it does not, record that and use manual entry,
   as the phase-2 Moonraker checklist allows. A real OctoPi would give
   stronger discovery evidence.
3. **Service outage.** Run `podman stop farm3d-a02-octoprint`. The card
   should go to Error, and reconnect attempts should back off.
   `podman start` should recover it without restarting farm3d.
4. Record the results, screenshots (`docs/screenshots/a0-2-*.png`), and the
   commit tested here.

## How the implementation differs from the plan

The plan predates P1–P5. What changed and why:

- **Trait shape.** The plan targeted `subscribe(Sender<PrinterStatus>)`.
  The current trait sends `ConnectionObservation`s. Each poll now sends
  `Telemetry` (the normalized `PrinterTelemetry`) and then `Health` (the
  serial-link state), in the same order Moonraker uses. The trait itself
  did not change. `status_from` became `telemetry_from` plus
  `connection_state_from_job_state`.
- **State vocabulary.** P1 added `HostActivity`, so OctoPrint's job-state
  strings are normalized inside the adapter:
  Operational→Idle, Printing*→Printing, Paused→Paused,
  Pausing/Resuming/Cancelling/Finishing/Starting*/Sending*→Busy, and
  anything else →Unknown. Connection state: `Offline`/`Closed`→Offline;
  `Error*` and `Offline after error`→Error; `Opening serial`/`Detecting`/
  `Connecting`→Connecting; anything else→Online.
- **Registration.** The plan named two registration points. The code now
  had five "is this Moonraker?" gates: create, batch, connection edit,
  setup gaps, and the factory. They now share one `SUPPORTED_KINDS` list,
  and a test ties that list to the factory. The factory is public as
  `supervisor::build_connection` so integration tests can use it.
- **HTTP client.** The plan used `reqwest 0.12` with default features. This
  change uses `reqwest 0.13`, which is already in the lockfile through
  Tauri, with `default-features = false`: no TLS backend, no system-proxy
  lookup. `useTls: true` is refused with a clear `Unreachable` error.
  Moonraker's `wss://` has the same limit today (tokio-tungstenite is
  built without TLS). Redirects are not followed and proxies are bypassed,
  because reqwest does not strip a custom `X-Api-Key` header on a
  cross-host redirect.
- **Tests.** The plan said not to use a mock HTTP server. A small loopback
  stub was added anyway. It covers what the pure module cannot: which
  status codes map to which errors, what goes on the wire, and 409
  tolerance inside the poll loop. The live tests are the real evidence.

## Known limits

- No TLS for either adapter (see above).
- No reverse-proxy subpath (e.g. `https://host/octoprint/`):
  `ConnectionConfig` has no path field.
- Validation used an admin user's key. The minimum OctoPrint permissions
  for `/api/job`, `/api/printer`, `/api/connection`, and
  `/api/printerprofiles` were not tested; Status plus Connection is the
  likely set. OctoPrint answers 403 whether a key is invalid or only
  under-permissioned, and both show as a credential error.
- `ProbeResult.firmware` is always empty for OctoPrint. The core API does
  not expose it.
